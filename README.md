# shopifytoodoo — Central Order Management

Download orders from **Shopify**, validate them, approve them and publish them
as **Odoo 19** sales orders — with the sales order head, the sales order lines,
the discounts and the financial transactions stored centrally so that every
amount can be checked *before* an order is accepted.

```
Shopify Admin API ──► central order tables ──► validation ──► approval ──► Odoo
   (GraphQL)             (Postgres / Neon)         (13 rules)   (threshold)   sale.order
                             │                                                      ├─ xmlrpc
                             │                                                      ├─ jsonrpc
                             │                                                      └─ DMF import file
                             └─ audit trail, publish history, pickings
```

---

## 1. What the solution does

| Capability | Where |
|---|---|
| Downloads Shopify orders with lines, discounts, tax, shipping, transactions and fulfilments | `src/integrations/shopify/` |
| Stores them in the central tables (`sales_order_head`, `sales_order_line`, `sales_order_discount`, `sales_order_transaction`, …) | `src/repositories/order-repository.ts` |
| Validates every order against 13 executable rules | `src/domain/validation.ts` |
| Applies the approval threshold and the role based approval workflow | `src/services/approval-service.ts` |
| Builds the Odoo `sale.order` payload (head + lines, prices, discounts, taxes) | `src/domain/odoo-mapper.ts` |
| Publishes through the Odoo XML-RPC / JSON-RPC API **or** as a DMF import file | `src/services/publish-service.ts`, `src/domain/dmf.ts` |
| Confirms the sales order and reads the generated pickings back | `src/services/odoo-gateway.ts` |
| Records every action with the acting user and role | `audit_log` table |

## 2. Quick start (no credentials required)

```bash
npm install
npm run build
npm test                       # 79 executable tests
npm run sync -- --dry-run     # downloads the fixture orders and validates them
```

The solution starts with an embedded Postgres ([PGlite](https://pglite.dev)),
so `npm start` works with no external dependency:

```bash
npm start
curl -s localhost:8080/health
```

To run the whole pipeline offline against the bundled Shopify fixture and a
local Odoo, set the variables of `.env.example` (see §6).

## 3. End to end flow

1. **Download** — `POST /api/v1/orders/ingest` (or `npm run sync`) pulls the
   orders from the Shopify Admin GraphQL API and stores them.  Re-running the
   download updates the order in place: no duplicate lines, discounts or
   transactions are created.
2. **Validate** — `POST /api/v1/orders/:id/validate` runs the rule set.  A
   blocking failure stops the order before it can reach Odoo.
3. **Approve** — orders at or above the configured threshold need an explicit
   approval from an `approver`; orders below it are auto approved.
4. **Publish** — `POST /api/v1/orders/:id/publish` creates the Odoo sales
   order (head + lines), confirms it and stores the pickings.
5. **Audit** — every step is written to `audit_log` with the actor, the role,
   the entity and the result.

## 4. Data model

| Table | Odoo counterpart | Content |
|---|---|---|
| `sales_order_head` | `sale.order` | customer, addresses, totals, status, approval, Odoo ids, raw payload |
| `sales_order_line` | `sale.order.line` | SKU, quantity, list price, discount, tax, net price, Odoo product id |
| `sales_order_discount` | — | every discount with its code, allocation method, value and amount |
| `sales_order_line_discount` | — | the discount allocation per line |
| `sales_order_transaction` | — | the financial transactions (capture, refund, authorisation) |
| `sales_order_fulfillment` | — | the Shopify fulfilments and their tracking numbers |
| `sales_order_picking` | `stock.picking` | the pickings generated by Odoo |
| `sales_order_validation` | — | the result of every rule, per order |
| `publish_attempt` / `publish_artifact` | — | the publish history and the generated DMF files |
| `product_mapping` / `tax_mapping` | — | the Shopify → Odoo mappings |
| `app_user` / `app_setting` / `audit_log` | — | the API keys (hashed), the runtime settings and the audit trail |

All monetary values are stored as `numeric(20,4)` and are handled internally
as **integer minor units**, so no rounding drift is possible between the
Shopify totals, the discounts, the tax and the Odoo sales order.

## 5. The validation rules

| Rule | Severity | What it proves |
|---|---|---|
| `VAL-001` | blocking | the lines + tax + shipping add up to the order total |
| `VAL-002` | blocking | every line is internally consistent |
| `VAL-003` | blocking | the discounts add up to the discount reported by Shopify |
| `VAL-004` | blocking | every line has a positive quantity |
| `VAL-005` | blocking | quantities and prices are sane |
| `VAL-006` | blocking | the customer can be identified |
| `VAL-007` | blocking | the currency is supported by the target instance |
| `VAL-008` | blocking | every line is mapped to an Odoo product |
| `VAL-009` | blocking | every tax is mapped to an Odoo tax |
| `VAL-010` | blocking | the order is stored exactly once |
| `VAL-011` | warning | the payments reconcile with the total |
| `VAL-012` | warning | every discount carries an amount and a scope |
| `VAL-013` | info | the fulfilment status is reported |

## 6. Configuration

Copy `.env.example` to `.env`.  The most important variables:

| Variable | Purpose |
|---|---|
| `DATABASE_URL` | Neon / Postgres connection string (empty = embedded PGlite) |
| `SHOPIFY_SHOP_DOMAIN`, `SHOPIFY_ACCESS_TOKEN` | the Shopify Admin API credentials |
| `SHOPIFY_FIXTURE` | serve the orders from a local file (offline demo / tests) |
| `ODOO_URL`, `ODOO_DB`, `ODOO_USERNAME`, `ODOO_PASSWORD` | the Odoo external API |
| `ODOO_PROTOCOL` | `xmlrpc` (default) or `jsonrpc` |
| `ADMIN_API_KEY`, `OPERATOR_API_KEY`, `APPROVER_API_KEY`, `AUDITOR_API_KEY` | the API keys (stored hashed) |
| `APPROVAL_THRESHOLD_AMOUNT` | the approval threshold, in major units |

Runtime settings (threshold, Odoo ids, fallbacks) can also be changed through
`PUT /api/v1/settings` without a redeploy.

For a serverless deployment the variables are applied to the Vercel projects
with the helper below (the secrets stay out of the repository):

```bash
cp .env.example .env.vercel.local     # edit it: DATABASE_URL, the API keys, …
npm run vercel:env -- --env-file .env.vercel.local          # dry run
npm run vercel:env -- --env-file .env.vercel.local --apply  # apply
```

The details are in [docs/vercel-deployment.md](docs/vercel-deployment.md).

## 9. Deployment

Two entry points are shipped, and both default-export a request handler so
that the service runs unchanged as a long running server or as a serverless
function:

| Target | Command | Entry point |
|---|---|---|
| Node / Docker | `npm start` (or `docker compose up -d`) | `src/server.ts` → `dist/server.js` |
| Serverless (Vercel, Lambda, …) | the platform loads the entry module | `src/app.ts` (default export) or `src/index.js` (re-export) |

The serverless entry point creates the container on the first request and
reuses it while the instance stays warm; the details are in
[docs/vercel-deployment.md](docs/vercel-deployment.md).
